# s10 - Task System

## 1. 一句话核心

把"大目标拆成小任务、排序、持久化"——**文件持久化的任务图**：每条任务有自己的 ID 和状态，`blockedBy` 记录前置依赖，`owner` 记录负责的 agent，这是多 agent 协作的基础。

教材：*"Break big goals into small tasks, order them, persist"* — File-persisted task graph, the foundation for multi-agent collaboration；Harness Layer 定位 **Tasks — Persisted goals, recoverable progress**（README 第 7 行）。动机：s05 的 TodoWrite 只记录"当前任务"的检查项，**不知道任务间关系**——"写 API"要等"建表"、"写测试"要等 API 稳定，TodoWrite 无法表达这种依赖，也无法记录谁负责（README 第 13-21 行）。

本项目实现见 [s10_task_system.py:563-729](s10_task_system.py#L563-L729)（Task + TaskStore + 核心函数）、[s10_task_system.py:1132-1191](s10_task_system.py#L1132-L1191)（5 个 task 工具定义）、[s10_task_system.py:1193-1240](s10_task_system.py#L1193-L1240)（工具 handler）。

## 2. TodoWrite vs Task System 对比（s05 → s10 演进）

教材 README 第 31-42 行：

| | TodoWrite (s05) | Task System (s10) |
|---|---|---|
| 角色 | 当前任务的执行检查清单 | 可恢复的任务系统 |
| 存储 | 进程内 / 会话状态 | `.tasks/{id}.json` |
| 依赖 | 无 | `blockedBy` 依赖图 |
| 生命周期 | 当前会话 / 当前任务 | 跨会话 |
| 协作 | 无认领 | `owner` / claim |
| 状态 | pending / in_progress / completed | 同左 |
| 粒度 | agent 自己的步骤 | 可认领、可跟踪、可解锁的任务 |
| 更新契约 | 替换整个清单 | 逐条 create/get/update/list |

**本质区别**：TodoWrite 是"当前 agent 当前任务的便签"（s05 实现 [s10_task_system.py:792-843](s10_task_system.py#L792-L843) 保留），Task System 是"跨进程、可被多个 agent 认领、带依赖关系"的持久状态。

## 3. Task 数据结构（6 字段 + ID 排他创建）

```python
@dataclass
class Task:                       # [s10_task_system.py:563-571]
    id: str                       # task_ + 8 位随机 hex
    subject: str
    description: str
    status: str                   # pending | in_progress | completed
    owner: str | None             # 认领该任务的 agent
    blockedBy: list[str]          # 依赖的任务 ID 列表
```

- **ID 生成**：`task_{uuid.uuid4().hex[:8]}`（[s10_task_system.py:614](s10_task_system.py#L614)）。教材用 `secrets.token_hex(4)`（code.py L114），等价 8 位 hex
- **ID 排他创建**（教材 README 第 65 行 "Files are created exclusively; an existing ID is discarded and regenerated"）：`open("x", ...)` 独占创建，撞 `FileExistsError` 就**重新生成 ID**、重试最多 100 次（[s10_task_system.py:621-626](s10_task_system.py#L621-L626)）——绝不覆盖已有任务
- **ID 校验**：`TASK_ID_PATTERN = ^task_[0-9a-f]{8}$`（[s10_task_system.py:560](s10_task_system.py#L560)），`_path` 里正则 + `resolve().is_relative_to(root)` 双重把关（[s10_task_system.py:588-595](s10_task_system.py#L588-L595)）
- **load 校验**：读文件后核对 `task.id == task_id` 且 status 在三态内（[s10_task_system.py:635-642](s10_task_system.py#L635-L642)）——防文件被改坏

## 4. 3 状态 + 2 动作状态机

教材 README 第 148-157 行：

```
pending ──claim──→ in_progress ──complete──→ completed
```

- **claim**（动作）：`pending → in_progress`，设 owner，开始干活
- **complete**（动作）：`in_progress → completed`，标记完成并解锁下游

状态机是**单向严格**的：claim 只能从 pending 来（非 pending 拒绝，[s10_task_system.py:691-692](s10_task_system.py#L691-L692)），complete 只能从 in_progress 来（非 in_progress 拒绝，[s10_task_system.py:705-706](s10_task_system.py#L705-L706)）。

## 5. can_start / claim / complete 三个关键函数

### ① can_start（[s10_task_system.py:684-686](s10_task_system.py#L684-L686)）
```python
def can_start(task_id: str) -> bool:
    return not incomplete_dependencies(load_task(task_id))
```
`incomplete_dependencies`（[s10_task_system.py:672-681](s10_task_system.py#L672-L681)）遍历 `blockedBy`，依赖不是 completed、或文件缺失（`FileNotFoundError/ValueError`）都算未完成。

### ② claim_task（[s10_task_system.py:689-700](s10_task_system.py#L689-L700)）
三道检查 + 更新：非 pending 拒绝 → 依赖未完成返 `Blocked by: ...` → 通过则设 owner + `status=in_progress` + `TASKS.save`。**失败返回错误消息字符串，不抛异常**——模型能读到错误自我修正。

### ③ complete_task（[s10_task_system.py:703-729](s10_task_system.py#L703-L729)）
检查 status==in_progress、owner 匹配 → 完成前算 `ready_before` 集合 → 置 completed 并 save → **前后对比**找出刚解锁的下游。返回 `Completed {id} ({subject})` + 可选 `Unblocked: ...`。

## 6. 文件命名：{id}.json（不是 slug 化）—— 跟 blockedBy ID 引用匹配

实现：`_path` 返回 `root / f"{task_id}.json"`（[s10_task_system.py:592](s10_task_system.py#L592)），教材明确 "writes `.tasks/{id}.json`"（README 第 77 行）。

**为什么不能按 subject slug 命名**：`blockedBy` 用 **ID** 引用依赖，claim/complete 要按 ID `load` 文件——文件名 = ID + `.json` 直接可寻址。若文件名是 slug 化 subject：
- `load(task_id)` 无法从 ID 反查文件（除非扫描全部文件读 id 建索引）
- subject 可重复（两个"fix bug"任务 slug 撞名）、可含路径分隔符/非法字符
- ID 本身不可读但**稳定**；subject 是业务描述，**不稳定**

对比 s09 memory：memory 用 **slug 文件名**（[s09_memory.py:161-163](s09_memory.py#L161-L163)），因为按 name 读、且 `MEMORY.md` 索引里存了 filename 映射。**两种文件命名策略取决于"引用键是什么"**：memory 的引用键是 name（slug 化），task 的引用键是 ID（直接当文件名）。

## 7. complete 时 unblock 算（前后对比 ready 集合）

教材 code.py L209-222。为什么必须**前后对比**：完成一个任务可能同时解锁多个下游，但如果某个下游**在完成前就已经 ready**（比如它只依赖一个早已 completed 的任务，本次完成的是另一个无关任务），它不该被算作"本次解锁"。

```python
ready_before = {candidate.id for candidate in list_tasks()      # 完成前已 ready 的
                if candidate.status == "pending"
                and candidate.blockedBy and can_start(candidate.id)}
task.status = "completed"; TASKS.save(task)
unblocked = [c.subject for c in list_tasks()                     # 完成后新增 ready 的
             if c.status == "pending" and c.blockedBy
             and c.id not in ready_before and can_start(c.id)]
```
（[s10_task_system.py:710-723](s10_task_system.py#L710-L723)）。只有 `id not in ready_before` 才算"本次刚被解锁"，避免重复/误报。

## 8. owner 字段的设计意图（为 s13 agent teams 铺路）

- `owner` 记录认领者：claim 时设 `owner`（[s10_task_system.py:696](s10_task_system.py#L696)），list 显示 `[owner]`（run_list_tasks [s10_task_system.py:1201-1212](s10_task_system.py#L1201-L1212)）
- **complete 校验 owner**（[s10_task_system.py:707-708](s10_task_system.py#L707-L708)）：`task.owner != owner` → 拒绝。防"A 认领、B 抢着 complete"——教材 README 第 7 行把任务图定义为 *foundation for multi-agent collaboration*
- 当前单 agent 场景：工具层 `run_claim_task`/`run_complete_task` 固定 `owner="agent"`（[s10_task_system.py:1218-1224](s10_task_system.py#L1218-L1224)），但 `claim_task(task_id, owner)` 函数签名已预留 owner 参数——多 agent 时传各自身份即可
- 设计意图：owner 让"谁负责"成为任务状态的一部分，跨会话/跨 agent 可追溯（[❓ 用户补充：你说 s13 是 agent teams，这节的标题按此写——教材目录链到 s13 的具体内容我未确认，见第 12 节]）

## 9. OpenAI 协议差异（重点：完整文件读、状态变更）

**s10 的 task 工具是纯本地文件操作，不调模型**——所以没有 OpenAI 响应提取的适配，协议差异回到通用点：

| 维度 | 本项目（OpenAI） | 教材（Anthropic） |
|---|---|---|
| 工具 schema | `{"type":"function","function":{"parameters"}}` | `{"name","input_schema"}` |
| 工具结果 | `role=tool` 独立消息 | user 消息 content 里 `tool_result` block |
| system | `messages[0]`（压缩保留那套 s09 已做） | `create(system=...)` 独立参数 |
| 判断停止 | `not msg.tool_calls` | `stop_reason != "tool_use"` |

**完整文件读**（用户标注重点）：`get_task` 返回**完整** JSON（`asdict` 全 6 字段，[s10_task_system.py:668-669](s10_task_system.py#L668-L669)），`TaskStore.load` 完整读 + 双校验（[s10_task_system.py:635-642](s10_task_system.py#L635-L642)）——task 文件小，不做 s08 式的截断/预览。跨会话恢复时模型用 `get_task` 读完整描述继续干活（教材 README 第 138-146 行）。

**状态变更**（用户标注重点）：claim/complete 是**状态机动作**，改字段后 `TASKS.save(task)` **全量重写**整个 JSON 文件（[s10_task_system.py:629-633](s10_task_system.py#L629-L633)）；校验逻辑在函数层（`claim_task`/`complete_task` 返回错误消息），工具层 `run_*` 只做薄转发。错误消息进 `tool` 消息返回给模型，模型据此调整。

## 11. N 个最佳实践亮点

1. **ID 排他创建不覆盖**（[s10_task_system.py:621-626](s10_task_system.py#L621-L626)）：`open("x")` + 撞了重生成，绝不覆盖已有任务——"create 是分配新身份，不是改旧任务"
2. **`_path` 双校验**（[s10_task_system.py:588-595](s10_task_system.py#L588-L595)）：ID 正则 `fullmatch`（挡住路径分隔符/非 hex）+ resolve 后仍在 root 内——任务路径不可穿越工作区
3. **依赖完整性**：create 时校验依赖存在（[608-609](s10_task_system.py#L608-L609)）；load 时校验 id 匹配 + status 合法（[638-641](s10_task_system.py#L638-L641)）
4. **`incomplete_dependencies` 把文件缺失算未完成**（[s10_task_system.py:679-680](s10_task_system.py#L679-L680)）：依赖文件被删/损坏，任务照样不能 claim——不放过任何阻塞
5. **claim/complete 失败返错误消息不抛异常**：模型读到 `Blocked by: ...` / `owned by ...` 能自我修正
6. **unblock 前后对比**（[s10_task_system.py:710-723](s10_task_system.py#L710-L723)）：只报本次新解锁的，不重复不误报
7. **owner 校验防抢任务**（[s10_task_system.py:707-708](s10_task_system.py#L707-L708)）：complete 必须 owner 匹配
8. **状态机严格单向**：claim 只认 pending、complete 只认 in_progress，非法状态直接拒绝
9. **全量 save**（[s10_task_system.py:629-633](s10_task_system.py#L629-L633)）：状态变更重写整个 JSON——task 文件小，简单可靠，避免部分更新的一致性麻烦
10. **system 里教工具用法**（[s10_task_system.py:732-752](s10_task_system.py#L732-L752)）：模型启动就知道 task 工具怎么用
11. **文件即真相**：`.tasks/` 就是持久状态，新进程 `TaskStore.list()` 即恢复进度——跨 session 恢复不需要额外快照机制
