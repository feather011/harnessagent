# s15 - Integrated Harness 我的理解

## 1. 一句话核心

**"多种机制，一个循环"**——s15 不引入新机制，**把 s14 已经实现的 28 工具 + MCP + cron + background + team + 记忆 + 压缩 全部摆到 6 个显式钩子点 + 3 个组装器的骨架里**。s15 主文件 190 行，**不动 s14 一行代码**（`git diff s14_mcp_plugin.py` 为空）。

教材原话：*"Many mechanisms, one loop"* — tools, permissions, memory, tasks, teams, and plugins all hang off the same `while True`。Harness Layer 定位 **Integration**——把已有机制接入同一个 runnable system。

本项目实现见 [s15_integrated_harness.py:33-48](s15_integrated_harness.py#L33-L48)（4 薄包装钩子）、[s15_integrated_harness.py:54-70](s15_integrated_harness.py#L54-L70)（drain_events）、[s15_integrated_harness.py:74-75](s15_integrated_harness.py#L74-L75)（_compaction_step）、[s15_integrated_harness.py:97-105](s15_integrated_harness.py#L97-L105)（assemble_system_prompt 7 段）、[s15_integrated_harness.py:117-184](s15_integrated_harness.py#L117-L184)（主循环）。

## 2. s15 的"6 钩子 + 3 组装器"骨架

## 4. drain_events 收口 3 事件源（[L54-70](s15_integrated_harness.py#L54-L70)）

```python
def drain_events() -> list[dict]:
    events = []
    # cron：沿用 s14 SCHEDULER.consume_queue + "[Scheduled] {prompt}" 既有格式
    for job in s14.SCHEDULER.consume_queue():
        events.append({"role": "user", "content": f"[Scheduled] {job.prompt}"})
    # background：沿用 s14 collect_background_results 既有完整 <task_notification> XML
    bg_msgs = s14.collect_background_results()
    if bg_msgs:
        events.append({"role": "user", "content": "\n\n".join(bg_msgs)})
    # team：沿用 s14 consume_lead_inbox + format_team_events
    inbox = s14.consume_lead_inbox()
    if inbox:
        events.append({"role": "user", "content": s14.format_team_events(inbox)})
    return events
```

**3 个"沿用"**：
- 字符串格式完全沿用（`[Scheduled] {prompt}` / `<task_notification>` / `[Team events]`）
- s14 既有的 consume/collect 函数直接调用
- 不发明新 XML/标签

**s15 之前散落在 3 个不同地方**（s11 `<task_notification>` 在 BackgroundManager、s12 `[Scheduled]` 在 agent_loop 顶部、s13 `[Team events]` 在 CLI 主循环的 BUS.peek 分支）——s15 把它们**收口到一个函数**。

## 5. agent_loop 6 钩子点串接（[L117-184](s15_integrated_harness.py#L117-L184)）

```python
def agent_loop(messages, active_request):
    reactive_retries = 0
    while True:
        # 钩子 1
        if active_request and not active_request.startswith("("):
            _hook_user_prompt_submit(active_request)
        # 钩子 2
        for ev in drain_events():
            messages.append(ev)
        # 钩子 3
        messages[:] = _compaction_step(messages, active_request)
        # 重组 system prompt（每轮重拼，mcp status / tools 会变）
        tools, handlers = s14.assemble_tool_pool()
        system_prompt = assemble_system_prompt({"tools": tools})
        if messages and messages[0].get("role") == "system":
            messages[0]["content"] = system_prompt
        else:
            messages.insert(0, {"role": "system", "content": system_prompt})
        # LLM + reactive 限流
        try:
            resp = client.chat.completions.create(model=MODEL, messages=_strip_surrogates(messages), tools=tools, max_tokens=8000)
            reactive_retries = 0
        except Exception as error:
            too_long = any(t in str(error).lower() for t in ("prompt_too_long", "too many tokens"))
            if too_long and reactive_retries < MAX_REACTIVE_RETRIES:
                messages[:] = s14.COMPACTOR.reactive_compact(messages, active_request)
                reactive_retries += 1
                continue
            raise
        # 处理响应
        msg = resp.choices[0].message
        messages.append(_strip_surrogates(msg.model_dump(exclude_none=True)))
        # 钩子 6（无 tool_calls）
        if not msg.tool_calls:
            force = _hook_stop(messages)
            if force: messages.append({"role": "user", "content": str(force)}); continue
            if msg.content: print(_strip_surrogates(f"\033[32m{msg.content}\033[0m"))
            s14.extract_memories(messages)
            return
        # 钩子 4+5
        for call in msg.tool_calls:
            name, args = call.function.name, json.loads(call.function.arguments)
            if (blocked := _hook_permission(name, args)) is not None:
                messages.append({"role": "tool", "tool_call_id": call.id, "content": str(blocked)}); continue
            output = s14.execute_named(handlers, name, args)
            _hook_log_tool_call(name, args, output)
            messages.append({"role": "tool", "tool_call_id": call.id, "content": output})
```

**与 s14 agent_loop 的差异**：
- 5 个 hook 位置用薄包装函数调用（结构对称）
- 2 个新位置（drain / compaction）显式化为独立函数
- system prompt 改为**每轮重拼**（s14 是 startup 一次固定）
- reactive 限流保留（`MAX_REACTIVE_RETRIES`）
- extract_memories 调了，**consolidate_memories 缺**（见 §6 已知缺口）

## 6. 已知缺口（[❓ 待补]）

s15 agent_loop **重写而不是委托 s14.agent_loop**，导致丢了 3 处 s14 内联逻辑：

| 缺失逻辑 | s14 位置 | s15 影响 | 修复建议 |
|----------|----------|----------|----------|
| `should_run_background` 分支 | [L3573-3583](s14_mcp_plugin.py#L3573-L3583) | bash 传 `run_in_background=true` 不会被识别为后台，会当普通 bash 执行（长时间阻塞） | 在 `_hook_permission` 之后加 `if should_run_background(name, args): start_background_task(...)` |
| `compact` 工具特判 | [L3551-3555](s14_mcp_plugin.py#L3551-L3555) | 模型调 compact 工具会被 execute_named 报"unknown tool" | 加 `if name == "compact": output = "Compaction requested after this tool batch."` |
| `consolidate_memories` 调用 | [L3544-3545](s14_mcp_plugin.py#L3544-L3545) | 记忆只 extract 不 consolidate，长期会重复 | 改 `s14.extract_memories(messages)` 为 `if s14.extract_memories(messages): s14.consolidate_memories()` |

**`had_teammates` shutdown 退出条件**（[L3689](s14_mcp_plugin.py#L3689)）s15 CLI 主循环已经处理（[L240-243](s15_integrated_harness.py#L240-L243)），不在缺口里。

**`_s14_inner_loop` 是死代码**（[L108-113](s15_integrated_harness.py#L108-L113)）——定义了但 s15 agent_loop 没调用它。可以删，或者改造为"s15 委托 s14 模式"的备选入口。

**38/38 验收测试没覆盖这些缺口**——纯 wiring 验证（6 钩子存在 + 4 薄包装 + 3 事件源 + 7 段 + 6 钩子源码 grep）通过即 OK。functional e2e 不存在（用户确认），这些缺口要等真实 LLM 调用才能暴露。

## 7. CLI 主循环（[L201-244](s15_integrated_harness.py#L201-L244)）

接管 s14 `__main__`：
- `history = [{"role": "system", "content": assemble_system_prompt({"tools": []})}]` 启动
- `s14.SCHEDULER.start()` 启 cron 线程
- `_stdin_reader` 线程读 stdin
- **Lead 邮箱优先**：每次循环先 `BUS.peek("lead")`，有 team event 就跑 `agent_loop(history, "(team events)")`
- **前台输入**：`agent_loop(history, q)`，`agent_lock` 保护

**与 s14 CLI 的差异**：
- s15 用 `assemble_system_prompt` 拼 system prompt（不是 s14 的 `build_system_prompt`）——但底层还是 s14 的 4 段
- `had_teammates` shutdown 退出条件沿用

## 10. 过程修正记录

**事故 A**：第一版 plan 的 agent_loop 草稿写了 `continue raise` 语法错误（`continue` 不能接表达式）。我 review 时发现，让 ClaudeCode 改为 `if too_long ...: ... continue; raise`。

**事故 B**：第一版 plan 写 `s14.collectBackground_results()` 函数名错（下划线错误）。改回 `s14.collect_background_results()`。

**事故 C**：第一版 plan 没意识到 s14 已经有 `build_system_prompt`（4 段）+ `agent_loop`（含 cron ack/restore/memory extract/bg dispatch/compact 工具特判全套），打算"全部从零写"。我 review 时指出，改为"扩展 build_system_prompt 到 7 段 + 6 钩子显式化 + 委托 s14 关键内联逻辑"。

**事故 D**：第一版 plan 漏掉 s14 `MAX_REACTIVE_RETRIES` 限流。改回沿用 s14 常量。

**事故 E**：第一版 plan 写 `s14.session_history` vs `history` 命名不一致。s15 用 `history` 局部（接受——CLI 入口用局部，s14.session_history 不被 s15 引用）。

## 11. 与 s16/s17 的连接

- **s16 Workflow Runtime**：s15 已经有 `assemble_system_prompt` + 6 钩子的清晰边界，s16 加 `Workflow` 工具只需在 s15 主循环里多一个"工作流模式分支"——所有机制（cron/bg/team）继续通过 drain_events 接入
- **s17 Goal Loop**：s17 的"目标-子目标"循环是 agent_loop 的扩展——在 s15 的 6 钩子骨架上，钩子 1（UserPromptSubmit）变"目标提交"，钩子 6（Stop）变"目标校验"
- **真实生产 agent**：s15 的"wiring 显式化"是 harness 的"协议层"——让 6 钩子点成为可观测、可拦截、可测试的"扩展点"，业务逻辑（agent 怎么选工具）保持可替换

## 12. 一句话回顾

s15 = **6 钩子显式 + 3 组装器收口 + 5 事件源 drain + 不动 s14 一行**。价值在"骨架清晰度"——任何后来人 5 分钟就能看明白整个 agent 的事件流、组装流程、扩展点。e2e 验证留给 s14 既有覆盖，s15 本身是"代码地图"而不是"新功能"。
