# s16 - Workflow Runtime 我的理解

## 1. 一句话核心

**"一次 tool_use，跑完一整套编排"**——在 s15 工具池加一个 `Workflow` 工具。模型只传 name + args（不能传代码），背后启动一个**可恢复的脚本运行时**，用 `agent/parallel/pipeline/phase/log/workflow` 6 个原语协调 N 次 agent 调用，**journal 记录 checkpoint 断点续跑**。

教材：*"The model decides each step; a script decides the orchestration."*；Harness Layer 定位 **Orchestration — run saved multi-agent scripts above the single-agent loop**。

本项目实现见 [s16_workflow_runtime.py:97-133](s16_workflow_runtime.py#L97-L133)（TaskStatus + LocalWorkflowTask）、[s16_workflow_runtime.py:184-189](s16_workflow_runtime.py#L184-L189)（stable_key）、[s16_workflow_runtime.py:192-211](s16_workflow_runtime.py#L192-L211)（SimpleJsonSchema）、[s16_workflow_runtime.py:213-305](s16_workflow_runtime.py#L213-L305)（AgentRunner + Real/Mock 实现）、[s16_workflow_runtime.py:306-388](s16_workflow_runtime.py#L306-L388)（RunContext 6 原语）、[s16_workflow_runtime.py:389-419](s16_workflow_runtime.py#L389-L419)（WORKFLOWS registry + validate_meta + workflow decorator）、[s16_workflow_runtime.py:472-516](s16_workflow_runtime.py#L472-L516)（WORKFLOW_TOOL_SCHEMA + run_workflow_tool）、[s16_workflow_runtime.py:527-598](s16_workflow_runtime.py#L527-L598)（agent_loop 主循环）。

## 2. 6 编排原语（[L306-388](s16_workflow_runtime.py#L306-L388)）

| 原语 | 实现 | 作用 |
|------|------|------|
| `ctx.agent(prompt, {schema, label, phase})` | L320 算 stable_key → 查 journal → 命中返回 / 未命中 RealAgentRunner.run | 派一个子 agent，可选 JSON schema 校验 |
| `ctx.parallel(thunks)` | ThreadPoolExecutor + `ex.map` 收集 | **等齐屏障**：所有 thunks 并行跑，**一起等** |
| `ctx.pipeline(items, *stages)` | ThreadPoolExecutor + 每 item 走完所有 stage | **不等齐**：每 item 独立跑完所有 stage，**不等齐** |
| `ctx.phase(title)` | emit "phase" 事件 | 标记进度阶段（仅 UI） |
| `ctx.log(message)` | emit "log" 事件 | 打日志（仅 UI） |
| `@workflow(meta)` | 装饰器注册到 WORKFLOWS | 嵌套子工作流（**只支持 1 层**） |

**何时用 `parallel` vs `pipeline`**（教材重点）：
- **`parallel`**：下一步**需要**所有上一步结果 → 等齐屏障（如 review-changes 末尾"等所有 verify 完成才合并"）
- **`pipeline`**：每个 item **独立**走相同 stages → 不需要等齐（如 review-changes 每个 dimension 独立走 audit → verify，dim A 到 stage 3 时 dim B 可能还在 stage 1）

## 3. 4 个核心组件

### ① `LocalWorkflowTask` 状态机（[L105-133](s16_workflow_runtime.py#L105-L133)）

```python
class TaskStatus(str, Enum):
    PENDING = "pending"
    RUNNING = "running"
    COMPLETED = "completed"
    FAILED = "failed"

class LocalWorkflowTask:
    run_id, name, status, args, progress[], tokens, agents_used, error
```

`register_task(name)` → `start_task` → `mark_completed/mark_failed` 状态机推进。**内存存 `scheduler_tasks: dict[run_id, LocalWorkflowTask]`**——不持久化（snapshot 持久化）。

### ② `WorkflowJournal` + stable_key（[L162-189](s16_workflow_runtime.py#L162-L189)）

```python
def stable_key(kind, label, prompt, schema_repr=""):
    basis = f"{kind}|{label}|{prompt}|{schema_repr}"
    return f"{kind}-{int(hashlib.sha256(basis.encode()).hexdigest(), 16) % 10**10:010d}"
```

**SHA256 稳定哈希**——`kind|label|prompt|schema` 任一变化 → 完全不同 key。`% 10**10` 截断到 10 位数字。

**为什么不按完成顺序计数**：parallel/pipeline 里 agent 完成顺序不确定，"第 n 个完成"当 key 会让两次跑缓存对错位。**key 必须是基于内容的稳定哈希**。

journal 行格式：
```json
{"key": "agent-0123456789", "value": {...}, "ts": 1234567890}
```

3 类 kind：`agent_call` / `phase` / `workflow`。**每次 `record()` 立即 `flush()`**——中断能恢复。

### ③ `SimpleJsonSchema` 校验（[L192-211](s16_workflow_runtime.py#L192-L211)）

校验 `required` + `types`（string/int/list/bool/dict），**不支持嵌套**（简化版）。**不匹配 → 重试 1 次**（加"返回合法 JSON"提示）→ 还不对就 raise `WorkflowInputError`。

**为什么 1 次重试**：典型 LLM 99% 一次能返对，2 次以上会拖慢 workflow。

### ④ `AgentRunner` 抽象（[L213-305](s16_workflow_runtime.py#L213-L305)）

```python

## 5. journal 存储（`.runtime/`）

每次运行 4 个文件：

| 文件 | 内容 |
|------|------|
| `<run_id>.json` | 快照（workflow 名 + args + task state） |
| `<run_id>.output.json` | 最终输出 |
| `<run_id>.journal.jsonl` | journal（每行一条 agent/phase/workflow） |
| `<run_id>.lock` | 跨平台独占锁（**s13 双锁风格** + L49-94 抽象层） |

**新建运行**：先 `O_EXCL` 创建 runId（并发安全）→ 持 lock 整次执行 → 最终持久化释放。**沿用 s13 的 fcntl/msvcrt 跨平台文件锁**（[L49-94](s16_workflow_runtime.py#L49-L94)）。

**续跑**：带 `resume_from_run_id` → 读旧 snapshot 验证 → 重跑脚本但每个 `agent()` 命中 journal 就直接返回。

## 6. review-changes sample（[L696-738](s16_workflow_runtime.py#L696-L738)）

DIMENSIONS = ["security", "performance", "style", "error-handling", "testing"]

@workflow({"name": "review-changes", "description": "...", "phases": ["Review", "Verify"]})

        return {"dimension": dimension, "findings": out["findings"]}
    
    async def verify(audited, dimension, _i):
        ctx.phase("Verify")
        verdicts = await ctx.parallel([...每个 finding 独立 verify...])
        return {"dimension": dimension, "confirmed": [f for f, v in zip(...) if v and v["isReal"]]}
    
    results = await ctx.pipeline(DIMENSIONS, audit, verify)

```

**5 个维度并行 audit → 每个维度内 findings 串行 verify**（先 parallel 再 pipeline 嵌套）。

## 10. 过程修正记录（4 个 fix）

**事故 A（regex 错位）**：
- 错误：`_SLUG = re.compile(r"[^a-zA-Z0-9_-]")` 是**否定字符类**
- 后果：`fullmatch` 对任何字符串都返 True（含一个非合法字符也算"全是非合法字符"——但 `[^a-zA-Z0-9_-]` 匹配"非合法字符"，所以 `fullmatch("abc")` 返 False，因为 `abc` 全是合法字符不在 `[^...]` 里）
- **实际后果**：`_SLUG.fullmatch("abc")` 返 False（被否定类拒绝），`fullmatch("ab!c")` 返 True（含非合法字符，匹配 `[^...]`）—— **校验结果完全反了**
- 修复：`r"^[a-zA-Z0-9_-]+$"`（肯定字符类）

**事故 B（phases=[] 漏空校验）**：
- 错误：`not all([])` 永远 False → `not all(...)` 不会触发空列表 raise
- 后果：phases=[] 静默通过
- 修复：`not phases or not all(isinstance(p, str) and p for p in phases)`

**事故 C（Mock schema 不匹配）**：
- 错误：测试 12/13 号 MockAgentRunner 返 `{"findings": "mock(p)"}` 但 FINDINGS_SCHEMA 要求 `findings: list`
- 修复：Mock 改成 `{"p": {"findings": []}}` 关键词匹配（按 prompt 中关键词决定返回内容） + 满足 schema

**事故 D（journal.unlink FileNotFoundError）**：
- 错误：unlink 不存在文件时抛 FileNotFoundError
- 修复：加 `if path.exists(): path.unlink()` 容错

## 11. 与 s17 的连接

s17 Goal Loop 是 s16 的"目标检查"扩展：
- s16 已经有"任务状态 + 进度事件 + journal"骨架
- s17 加一个"目标检查"小循环：每完成 N 步检查"既定目标是否达成" → 决定是否继续
- **Workflow 工具在 s17 仍然有效**——s17 的 Goal Loop 包在 s16 的 agent_loop 外面
- s17 不引入新工具，只在 s16 已有事件流上做"goal check"分支

## 12. 一句话回顾

s16 = **"多 agent 编排 + 断点续跑 + JSON 结构化"**。价值在"固定流程可编程 + 中断可恢复 + 输出可解析"。**`Workflow` 工具不替换 s15 主循环，只是多一个选项**——模型用不用、什么时候用，模型自己判断。
