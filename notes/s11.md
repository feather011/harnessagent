# s11 - Background Tasks

## 1. 一句话核心

慢操作进后台，Agent Loop 不阻塞。教材：*"Slow operations go to the background, the Agent Loop continues"* — Background threads run commands, and later turns collect completed results（README 第 7 行）。动机：装依赖/跑测试套件/构建可能要好几分钟，同步执行时 harness 卡在当前 tool call，直到命令结束才能继续下一个工具或下一轮（README 第 13-15 行）；如果后续工作不依赖该命令，没必要阻塞。

本项目实现见 [s11_background_tasks.py:1324-1423](s11_background_tasks.py#L1324-L1423)（BackgroundManager + 后台函数）、[s11_background_tasks.py:800-808](s11_background_tasks.py#L800-L808)（bash schema）、[s11_background_tasks.py:1769-1783](s11_background_tasks.py#L1769-L1783)（execute 分支）。

## 2. 同步 vs 后台对比（s04 同步 → s11 后台）

教材 README 第 29-36 行：

| | 同步 (s04) | 后台 (s11) |
|---|---|---|
| 慢操作 | 当前 tool call 阻塞 | 后台线程执行 |
| Agent Loop | 等命令返回 | 占位结果后继续 |
| 结果 | 命令完成后返回 | 先返 bg_id，后续轮次收集 |
| 决策标准 | — | bash `run_in_background` 参数 |

s11 的流程（README 第 118-136 行）：turn 1 `bash(npm install, run_in_background=true)` → 返 `bg_0001` → agent 继续干别的；turn 3 顶部 collect → `<task_notification>` 注入。

## 3. should_run_background 决策（显式 vs 隐式）

```python
def should_run_background(tool_name, tool_input) -> bool:
    return tool_name == "bash" and tool_input.get("run_in_background") is True
```
（[s11_background_tasks.py:1403-1405](s11_background_tasks.py#L1403-L1405)）

**必须显式为 `is True`**——`"true"` 字符串、`1`、`False` 都不算（函数级 5 例验证）。**harness 不再从 `install`/`build`/`test` 等关键词猜**（教材 README 第 54 行）——执行模式由 tool call 显式选择。

## 4. BackgroundManager.start + _run（daemon thread + Lock）

```python
class BackgroundManager:                      # [s11_background_tasks.py:1324]
    def __init__(self):
        self.tasks = {}        # task_id -> {tool_call_id, command, status}
        self.results = {}      # task_id -> 结果字符串
        self._ready = []       # 完成队列（待 collect）
        self._counter = 0
        self._lock = threading.Lock()
```

- **start**（[s11_background_tasks.py:1339](s11_background_tasks.py#L1339)）：`_counter+1` → `bg_{n:04d}` → 注册 task（status=running）→ 启 **daemon 线程**跑 `_run` → **立即返回 bg_id**（实测 0.00s，不等命令）
- **_run**（[s11_background_tasks.py:1357](s11_background_tasks.py#L1357)）：跑命令 → `_format_bash_result` → `status = "completed" if exit_code == 0 else "failed"`；异常也标 failed → 在 lock 内写 results + `_ready.append`（线程安全）

## 5. execute_tool 改造（1 路 → 2 路）

教材有独立 `execute_tool(block)`（README 第 94-114 行）。本项目 s10 把工具执行内联在 agent_loop 循环，s11 抽出 `call_tool` 处理同步路径，循环里加 background 分支（[s11_background_tasks.py:1769-1783](s11_background_tasks.py#L1769-L1783)）：

```python
if should_run_background(name, args):        # 2 路：后台
    command = str(args.get("command", ""))
    if any(d in command for d in DENY):
        output = "Error: Dangerous command blocked"
    else:
        task_id = start_background_task(command, call.id)
        output = f"[Background task {task_id} started] The result will be collected on a later turn."
else:                                        # 1 路：同步（call_tool 走 TOOL_HANDLERS）
    output = call_tool(name, args)
```

`PreToolUse` hook 仍在主线程跑（教材同：hook 在 choose 之前），所以后台命令同样过权限闸门；`PostToolUse` 对 placeholder 结果照常触发。

## 6. collect / inject_background_results（不阻塞 + 不叫醒）

- **collect**（[s11_background_tasks.py:1378](s11_background_tasks.py#L1378)）：从 `_ready` 出队完成的任务（pop task/results），格式化为 `<task_notification>` 列表。**出队即清空**，同一条不会重复投递
- **inject_background_results**（[s11_background_tasks.py:1416](s11_background_tasks.py#L1416)）：agent_loop **while 顶部**（每次 create 前）调用，把通知作为独立 user 消息 append
- **完成不叫醒**（教材 README 第 116 行）：后台任务完成不会自己唤醒 agent；`inject_background_results` 只在 agent loop 下次运行时收集

## 7. <task_notification> 格式（不复用 tool_use_id）

```xml
<task_notification>
  <task_id>bg_0001</task_id>
  <status>completed</status>
  <command>sleep 5</command>
  <summary>...</summary>
</task_notification>
```
（[s11_background_tasks.py:1391-1400](s11_background_tasks.py#L1391-L1400)）

**不复用 tool_use_id**（教材 README 第 92 行）：原 tool_use 已经用 placeholder tool_result 答过，一对一契约已满足；完成结果作为独立事件注入。一个 tool_use 永远只对应一个 tool_result。

## 8. process group 隔离（Windows taskkill / POSIX killpg）

- `_run_bash_process`（[s11_background_tasks.py:1280](s11_background_tasks.py#L1280)）：`Popen(..., start_new_session=True)` 让命令在自己的进程组；`communicate(timeout=120)`；finally 清理进程组
- `_stop_process_group`（[s11_background_tasks.py:1240](s11_background_tasks.py#L1240)）跨平台：**Windows 无 `os.killpg` → `taskkill /F /T /PID` 杀进程树**（POSIX 用 SIGTERM→SIGKILL killpg）
- `atexit` + SIGTERM handler（[s11_background_tasks.py:1273-1279](s11_background_tasks.py#L1273-L1279)）：进程退出清理所有残留 shell
- 教材明确这是生命周期清理，不是沙箱——进程再 create 新 session 可能逃出进程组（README 第 81 行）

## 9. OpenAI 协议差异

| 维度 | 本项目（OpenAI） | 教材（Anthropic） |
|---|---|---|
| 工具 schema | `{"type":"function","function":{"parameters"}}` + `run_in_background` boolean | `{"name","input_schema"}` + 同参 |
| 工具结果 | `role=tool` 独立消息 | user 消息 content list 里 `tool_result` block |
| notification 注入 | **append 独立 `role=user` 消息**（[s11_background_tasks.py:1416](s11_background_tasks.py#L1416)） | 合并进最近 user 消息的 content list（code.py L410-421） |
| 执行层 | 无独立 execute_tool，内联在 agent_loop + 抽 `call_tool`（[s11_background_tasks.py:1212](s11_background_tasks.py#L1212)） | `execute_tool(block)` 独立函数 |
| 判断停止 | `not msg.tool_calls` | `stop_reason != "tool_use"` |

**协议差异集中在注入方式**：OpenAI 下一条消息 content 是 str，notification 直接作为新 user 消息 append（相邻 user 消息模型可正常读）；Anthropic 下 tool_result 与 text block 共居一个 user 消息，通知作为 text block 追加。

## 11. N 个最佳实践亮点

1. **显式参数不猜**（[s11_background_tasks.py:1403-1405](s11_background_tasks.py#L1403-L1405)）：`is True` 严格判定，杜绝"猜测式后台"
2. **即返 placeholder 不等命令**：`[Background task bg_0001 started]` 立即返回，agent 继续
3. **daemon thread + Lock**：后台线程与主线程共享 tasks/results 全部走 `_lock`，多并发安全
4. **notification 不复用 tool_use_id**：一对一工具结果契约不被破坏
5. **完成不叫醒**：结果只在下一轮 inject 收集，agent 不被异步打断
6. **失败标 failed**：非零 exit_code / 异常都进 `failed` 分支
7. **进程组隔离 + 退出清理**（[s11_background_tasks.py:1240-1279](s11_background_tasks.py#L1240-L1279)）：`start_new_session` + atexit/SIGTERM/taskkill，不留孤儿进程
8. **多并发互不干扰**：每个任务独立 thread + task_id，函数级验证两条并发
9. **双层防御**：后台命令过 permission hook + execute 层内置 DENY
10. **placeholder 自解释**：告诉模型"结果会在后续轮次注入"，模型知道不是丢了

## 12. ⚠️ 主观理解待补充 [❓ 用户补充]

代码能客观看出的摩擦点（作为线索）：

- **后台完成不叫醒**：如果 agent 一直不进入下一轮（用户不输入），notification 一直不发——s11 依赖"有后续轮次"才投递，无法主动打断
- **subagent 不支持后台**：`SUB_HANDLERS["bash"] = run_bash` 同步忽略 `run_in_background`——子 agent 传了参数也同步跑
- **Windows taskkill 的可靠性**：bash 主进程退出后，`taskkill /T` 靠树根 PID 找子进程，孤儿进程可能逃掉（教材也承认进程组非沙箱）
- **`run_in_background=false` 进历史**：`msg.model_dump(exclude_none=True)` 会保留 `False`，后续轮次模型能看到这个参数

但以下主观问题请补充：

- **执行层内联 vs execute_tool 函数**：项目从 s02 一直内联，s11 只抽了 `call_tool` 管同步——你觉得该不该像教材那样抽完整的 execute_tool？[❓ 用户补充]
- **后台不叫醒**：真需要"命令一完成就唤醒"的场景怎么处理？（s12 cron 是定时唤醒，不是完成唤醒）[❓ 用户补充]
- **subagent 要不要也支持后台**？[❓ 用户补充]

## 13. 给后续章节的衔接点（s12 cron scheduler）

教材 README 的 "What's Next"（第 171-175 行）：后台任务解决"慢操作不阻塞"，但**不记录未来工作何时开始**，也没有组件持续检查时间。s11 是"命令启动后怎么跑"，s12 是"任务何时启动"。

- **s12 Cron Scheduler（下一章）**：注册 `cron` + `prompt`，到点把 `[Scheduled] run tests` 放进队列，agent 空闲时启动一轮——给 agent 一个闹钟
- **衔接关系**：s11 后台是"同一命令的异步执行"，s12 是"未来时刻的工作触发"；两者都不阻塞主 loop，但触发源不同（完成 vs 定时）
