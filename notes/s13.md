# s13 - Agent Teams

## 1. 一句话核心

**"一个 agent 装不下整个任务时，让 teammates 分工"**——持久的 teammates 在独立线程跑自己的 agent loop（WORK → IDLE → WORK），通过 `.mailboxes/` 文件邮箱与 Lead 双向通信，共享任务板原子认领，用 typed 协议（req_id）管控 shutdown 和方案审批。

教材：*"When one agent cannot hold the whole job, let teammates divide the work."* — Persistent teammates, shared task selection, optional worktrees, and coordination protocols；Harness Layer 定位 **Team — how multiple agents divide work, share state, and stay under Lead's control**（README 第 7 行）。动机（README 第 13-33 行）：用户描述的是目标（"重构后端，清理配置/认证/测试"），不是团队设计——harness 要回答谁决定并行、teammate 怎么保持身份、结果怎么回、空闲时怎么接活、冲突目录怎么办、shutdown/审批怎么可追溯。

本项目实现见 [s13_agent_teams.py:2426-2539](s13_agent_teams.py#L2426-L2539)（MessageBus + ProtocolState）、[s13_agent_teams.py:2705-2948](s13_agent_teams.py#L2705-L2948)（TeammateRuntime）、[s13_agent_teams.py:593-875](s13_agent_teams.py#L593-L875)（任务系统 + 双锁）。

## 2. s13 vs s06/s10 对比（subagent vs teammate；单 agent vs 团队）

**s06 subagent vs s13 teammate**（教材 README 第 84-91 行）：

| | s06 Subagent | s13 Teammate |
|---|---|---|
| 生命周期 | 一次调用后结束 | `WORK → IDLE → WORK` 直到 shutdown |
| 上下文 | 只存在一个任务 | 跨任务持久 |
| 通信 | 返回一个结果 | 收消息 + 发事件 |
| 协作 | 单向委托 | 与 Lead 双向 |

**s10 Task System vs s13**（教材 README 第 403-415 行）：单 agent 用 task 工具 → Lead + 持久 teammates；无通信 → 文件邮箱 + 运行时投递；仓库 WORKDIR → 认领的 Task 可选 worktree；当前 agent 输出 → 独立的 `result` 和 `idle_notification` 两个事件。

## 3. Lead + Teammate 架构（谁拥有对话、独立 loop）

- **Lead** 拥有用户对话（`session_history`），提议团队分工并**等用户确认**才 spawn（[s13_agent_teams.py:3411-3440](s13_agent_teams.py#L3411-L3440) system 引导明确 "wait for user's confirmation"）；`spawn_teammate` 后**结束当前轮**，运行时把团队事件注入下一轮——Lead 不轮询 teammate（教材 README 第 58-79 行）
- **Teammate** 各自独立 `messages`/`system`/`TEAMMATE_TOOLS`（10 个精简工具，[s13_agent_teams.py:2403-2408](s13_agent_teams.py#L2403-L2408)），在 daemon 线程跑 `work()`（单轮）→ `wait_for_work()`（IDLE）循环（[s13_agent_teams.py:2705-2948](s13_agent_teams.py#L2705-L2948)）
- **`lead` 和 `agent` 是保留名**（[s13_agent_teams.py:2440](s13_agent_teams.py#L2440)）：`lead` 是协调者邮箱，`agent` 是主 agent 身份；teammate 名不能撞
- spawn 前先 `claim_task` 初始任务，**claim 失败则不发**（[s13_agent_teams.py:2935-2944](s13_agent_teams.py#L2935-L2944)）；无任务的 teammate 用 workspace 工具会被要求先 claim

- **`check_inbox` 不是模型工具**（教材 README 第 155 行）：消息到达属于运行时，模型只处理已被注入进 context 的事件

## 5. ProtocolState + typed 协议（shutdown req_id）

```python
@dataclass
class ProtocolState:                         # [s13_agent_teams.py:2493]
    request_id: str
    type: str            # "shutdown" | "plan_approval"
    sender: str
    target: str
    status: str          # pending | approved | rejected
    payload: str
    work_version: int | None = None
    task_id: str | None = None
```

普通协作用自由文本，**shutdown/审批用结构化协议**（教材 README 第 304-337 行）：

```
shutdown:  Lead 建 pending → shutdown_request(带 req_id) → teammate 完成当前步骤
           → shutdown_response(req_id) → match_response 定位原请求 → approved → loop 退出
plan:      Lead → plan_request | teammate → plan_approval_request(req_id, plan)
           → Lead → plan_approval_response(req_id, approve) → teammate gate 释放
```

- **req_id 关联一问一答**：`match_response` 校验 type + 收发方 + status 都是 pending（[s13_agent_teams.py:2515-2539](s13_agent_teams.py#L2515-L2539)）——一个回复对应一个请求
- **type 防错配、status 防重复应用**
- **work_version**：claim/release 任务时 `advance_assignment_version` +1（[s13_agent_teams.py:620](s13_agent_teams.py#L620)），旧批准的 plan 失效——teammate 换任务后不能沿用旧方案

## 6. claim 原子双锁（RLock + fcntl/msvcrt）

教材 README 第 194-230 行：**发现（scan）和认领（claim）分离，认领必须原子**——多个 teammate 可能看到同一候选，但只有一个能把任务移到 in_progress。

```python
@contextmanager
def task_store_lock():                       # [s13_agent_teams.py:593]
    with task_lock:                          # 进程内 RLock（同进程线程互斥）
        ... _file_lock_acquire(handle)       # 文件锁（跨进程互斥）
```

`_file_lock_acquire`（[s13_agent_teams.py:586](s13_agent_teams.py#L586)）双保险：**POSIX 用 `fcntl.flock`，Windows 用 `msvcrt.locking`**（用户关键设计点）。`claim_task`（[s13_agent_teams.py:768](s13_agent_teams.py#L768)）在锁内做：pending + 无主 + owner 无在途 + 依赖完成 + worktree 可用 → 写文件（temp + os.replace 原子写）+ 绑定 assignment。

任务文件 `save_task` 也走 temp + `os.replace`（[s13_agent_teams.py:660-672](s13_agent_teams.py#L660-L672)）——同锁内原子替换，防半截文件。

## 7. plan gate（强制约束）

`_run_teammate_tool`（[s13_agent_teams.py:2593](s13_agent_teams.py#L2593)）在 Teammate 的工具 dispatch 里检查：

```python
gate = plan_gates.get(teammate, "not_required")
if name in {"bash", "write_file", "edit_file"}:
    if gate not in {"not_required", "approved"}:
        return f"Blocked: plan status is {gate}. Submit or revise the plan and wait for approval..."
```

- **状态**：`not_required` / `required` / `pending` / `approved` / `rejected`（[s13_agent_teams.py:2502](s13_agent_teams.py#L2502)）
- `required`/`pending`/`rejected` 时 teammate 能**读文件、提交/修改方案**，但不能 bash/write/edit（教材 README 第 366-368 行）
- `spawn_teammate(require_plan=True)` 线程启动前就激活 gate；`request_plan` 对运行中的 teammate 动态开启
- `complete_task` 也在 gate 未通过时拒绝完成（[s13_agent_teams.py:805-807](s13_agent_teams.py#L805-L807)）
- **Teammate 不读主终端**：`_run_teammate_tool` 用 `check_permission(prompt_user=False)`（[s13_agent_teams.py:1154](s13_agent_teams.py#L1154)）——危险命令直接拒绝并让 Lead 处理，不抢主终端 input

## 8. worktree 隔离（fail closed）

`Task.worktree` 可选（[s13_agent_teams.py:631](s13_agent_teams.py#L631)），Lead 用 `create_worktree`（Lead-only，[s13_agent_teams.py:969](s13_agent_teams.py#L969)）绑定 pending 无主任务：

- 校验：名字（1-64 字符无 `..`）、任务 pending 无主未绑定、git 仓库根、分支不存在、未注册（[s13_agent_teams.py:986-1016](s13_agent_teams.py#L986-L1016)）
- `git worktree add -b wt/<name> <path> HEAD` 创建；失败返回 **partial operation**（保留 checkout/branch 产物供人工恢复，任务保持 unbound）——**fail closed，绝不 fallback 到 WORKDIR**（教材 README 第 230 行）
- `task_worktree_cwd`（[s13_agent_teams.py:961](s13_agent_teams.py#L961)）：无 worktree → WORKDIR；绑定损坏 → 返回 error（claim 拒绝、工具报错）
- **claim 时把解析目录存进 `teammate_assignments[owner]`**，teammate 的 bash/read/write/edit/glob 全部从 assignment 读 cwd（[s13_agent_teams.py:2858-2880](s13_agent_teams.py#L2858-L2880)）
- **worktree 不是沙箱**（教材 README 第 288 行）：只隔离工作目录和分支，Shell 仍可访问父进程权限内的路径
- `remove_worktree`（Lead-only，[s13_agent_teams.py:1040](s13_agent_teams.py#L1040)）：拒绝 pending/in_progress 任务绑定、拒绝当前 turn 租约、未提交更改需 `discard_changes`；永远保留 `wt/<name>` 分支

## 9. IDLE 状态机（邮件箱 > 任务板）

`wait_for_work`（[s13_agent_teams.py:2827-2850](s13_agent_teams.py#L2827-L2850)）：

```
while True:
    inbox = BUS.wait_for_messages(name, IDLE_SCAN_INTERVAL)  # 先等邮件箱
    if inbox: handle → 有工作消息回 WORK；无变化继续
    task = claim_next_task(name)                              # 再扫任务板
    if task: [Auto-claimed task] 注入 → WORK
```

**IDLE 给消息优先级**（教材 README 第 170-192 行）：shutdown/plan 审批/Lead 直接指令应该先于机会性任务。`scan_unclaimed_tasks` 只扫描候选（[s13_agent_teams.py:2678](s13_agent_teams.py#L2678)），`claim_next_task` 逐个尝试认领（[s13_agent_teams.py:2692](s13_agent_teams.py#L2692)），一个 teammate 同时只有一个 assignment。

## 12. N 个最佳实践亮点

1. **claim 原子双锁**（[s13_agent_teams.py:593](s13_agent_teams.py#L593)）：RLock + 文件锁，跨线程跨进程只有一个认领成功——多 teammate 抢同一任务不冲突
2. **发现/认领分离**：scan 只出快照，claim 才改状态——候选过期由 claim 内部检查兜底
3. **一个 assignment 原则**：`_owner_in_progress` + `teammate_assignments` 双重检查，teammate 绝不能同时两个任务
4. **req_id typed 协议**（[s13_agent_teams.py:2515](s13_agent_teams.py#L2515)）：shutdown/plan 不用猜意图，一问一答可追溯
5. **work_version 失效旧批准**：换任务后旧 plan 批准自动作废
6. **worktree fail closed**（[s13_agent_teams.py:961](s13_agent_teams.py#L961)）：绑定损坏 → 报错，绝不悄悄把工作路由到仓库目录
7. **create_worktree 失败保留产物**（[s13_agent_teams.py:1031-1038](s13_agent_teams.py#L1031-L1038)）：partial operation 明说留了什么，人工可恢复
8. **remove_worktree 三重防线**（[s13_agent_teams.py:1051-1070](s13_agent_teams.py#L1051-L1070)）：活跃任务/当前租约/未提交更改都拒绝，永远保留分支
9. **IDLE 邮件箱优先**（[s13_agent_teams.py:2827](s13_agent_teams.py#L2827)）：shutdown/审批/指令先于机会性任务
10. **result 和 idle_notification 分离**（[s13_agent_teams.py:2815-2824](s13_agent_teams.py#L2815-L2824)）："这个任务产出了什么"和"还能接活吗"是两个事实，一个 "done" 表达不了

12. **线程只在 main 启动**（cron 线程 + teammate 线程），import 无副作用——函数级测试可安全 import

## 13. ⚠️ 主观理解待补充 [❓ 用户补充]

代码能客观看出的摩擦点（作为线索）：

- **teammate 是 daemon 线程，进程强退时不保证 `release_teammate_assignment` 执行完**——e2e 实测：强退后 `in_progress` 任务残留 `owner=worker`，下次 spawn 同名 teammate 时 `_owner_in_progress` 命中残留、claim 被拒（e2e 诊断发现，靠测试开头清理 `.tasks/` 绕开）
- **teammate 不持久化**：进程重启后 teammates 全部消失，只有任务（.tasks/）和 durable cron 保留——"跨 session durable 恢复"只针对任务状态，不是 teammate 身份
- **plan 审批依赖 Lead 及时处理**：teammate 提交方案后 `waiting_approval`，若 Lead 一直不 review，teammate 挂着
- **`run_agent_*` 的 assignment 对 Lead 是 WORKDIR**：Lead 自己 claim 任务时 cwd 会变成该任务目录（s12 的 cron scheduled turn 在 Lead 无 assignment 时正常）
- **worktree 需要 git 仓库**：非 git 目录 create_worktree 会失败（fail closed）

但以下主观问题请补充：

- **强退残留的 in_progress 任务**：要不要在启动时扫描"owner 不是任何 active teammate 的 in_progress 任务"并重置为 pending？[❓ 用户补充]
- **teammate 要不要做持久化恢复**（比如把 active_teammates 落盘，重启后恢复）？教材没做，但"跨 session durable"验收点你怎么理解？[❓ 用户补充]
- **plan gate 的 `work_version` 使旧批准失效**：teammate 换任务后旧 plan 作废是硬性要求，但如果新任务也简单，会不会过度约束？[❓ 用户补充]
- **broadcast 没有消息确认**：广播后无法知道谁收到了，重要指令要不要用 typed 协议逐个发？[❓ 用户补充]
- **e2e 里模型真的会主动提议团队 + 等确认吗**，还是用户明确要求才 spawn？[❓ 用户补充]
