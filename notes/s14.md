# s14 - MCP Plugin 我的理解

## 1. 一句话核心

**"把外部能力接进同一个 dispatch 框架"**——`MCPClient` 描述 server 工具列表 + 真实 handler；`assemble_tool_pool()` 每轮把已连 server 的工具按 `mcp__{server}__{tool}` 命名规范拼到 base pool 后，**agent_loop 只改 1 行**就能支持动态外部能力。授权由 host 的 `MCP_HOST_POLICY` 决定（精确 allowlist + 缺省 confirm），**不信 server 自己的 `readOnlyHint`/`destructiveHint`**。

教材原话：*"Harness Layer: Plugin — let the model reach external capability without rewriting the loop"*；动机（README 第 15-19 行）：外部工具来源不稳定（版本/重启/服务下线），harness 要回答"如何安全发现外部能力、命名怎么不撞车、授权边界怎么划、错误如何不挂 loop"。

本项目实现见 [s14_mcp_plugin.py:3081-3111](s14_mcp_plugin.py#L3081-L3111)（MCPClient）、[s14_mcp_plugin.py:3173-3187](s14_mcp_plugin.py#L3173-L3187)（connect_mcp）、[s14_mcp_plugin.py:3205-3246](s14_mcp_plugin.py#L3205-L3246)（assemble_tool_pool）、[s14_mcp_plugin.py:3249-3257](s14_mcp_plugin.py#L3249-L3257)（execute_named）。

## 2. MCPClient 三大职责 + 双 catch 异常边界

### ① server 元数据（[L3081-3099](s14_mcp_plugin.py#L3081-L3099)）

```python
class MCPClient:
    def __init__(self, name: str):
        self.name = name
        self.tools: list[dict] = []        # 工具 schema 列表（name + inputSchema + description + annotations）
        self._handlers: dict[str, callable] = {}  # 真实执行体
```

`register(tool_defs, handlers)` 强制做三道校验：
- 每个 tool 有非空 name（[L3091-3092](s14_mcp_plugin.py#L3091-L3092)）
- 同 server 工具名不重复（[L3093-3094](s14_mcp_plugin.py#L3093-L3094)）
- 每个 name 都有对应 handler（[L3095-3097](s14_mcp_plugin.py#L3095-L3097)）

**理解关键**：register 在 server 端做静态校验，runtime 只信任已注册成功的 server——把问题前置到"加载期"而不是"调用期"。

### ② 调用边界 = 异常转 tool_result（[L3101-3108](s14_mcp_plugin.py#L3101-L3108)）

```python
def call_tool(self, tool_name: str, args: dict) -> str:
    handler = self._handlers.get(tool_name)
    if not handler:
        return f"MCP error: unknown tool '{tool_name}'"
    try:
        return str(handler(**args))
    except Exception as exc:
        return f"MCP error: {type(exc).__name__}: {exc}"
```

**核心不变量**：MCPClient 永远不会 raise——所有异常转成 `MCP error: ...` 字符串，模型看到的是 tool_result 而不是 exception，**loop 不会被一个外部服务挂掉**。

### ③ 模块级注册表（[L3111-3112](s14_mcp_plugin.py#L3111-L3112)）

```python
mcp_clients: dict[str, MCPClient] = {}      # 已连 server
mcp_tool_policies: dict[str, str] = {}      # 工具名 -> allow/confirm
```

全局单例——agent loop 通过 `mcp_clients` 知道"现在哪些 server 是 active 的"。

### ④ execute_named 双 catch（[L3249-3257](s14_mcp_plugin.py#L3249-L3257)）

`MCPClient.call_tool` 已经把 handler 异常吞过一次；`execute_named` 又在外面套一层 try/except——**双 catch 是有意的**：
- 内层 catch：handler 抛错 → 转 MCP error 字符串
- 外层 catch：handler 自身代码 bug（如 kwargs 解析失败）→ 转 Error 字符串

任何一层挂掉都不会传到 agent_loop。两层错误前缀不同（`MCP error:` vs `Error:`），方便排错时定位是"server 内部问题"还是"dispatch 框架问题"。

## 3. 命名规范：`mcp__{server}__{tool}` + 64 字符限制

### 命名空间（[L3219](s14_mcp_plugin.py#L3219)）

```python
prefixed = f"mcp__{safe_server}__{safe_tool}"
```

**为什么是双下划线**：
- `mcp` 前缀：和 built-in 工具（`bash`/`read_file`/...）立即视觉分离
- `__` 分隔：模型在 system prompt 看到 `mcp__docs__search` 一眼就知道"这是 docs server 的 search 工具"，路由可以直接 split
- 双下划线而非单下划线：避免 `mcp_docs_search` 和"叫 `mcp_docs` 的 server 下的 `search` 工具"撞名

### normalize_mcp_name（[L3124-3129](s14_mcp_plugin.py#L3124-L3129)）

```python
_DISALLOWED_CHARS = re.compile(r"[^a-zA-Z0-9_-]")
def normalize_mcp_name(name: str) -> str:
    normalized = _DISALLOWED_CHARS.sub("_", name)
    if not normalized:
        raise ValueError("MCP names cannot normalize to an empty string")
    return normalized
```

只允许 `[a-zA-Z0-9_-]`，其他字符 → `_`。空串 raise。**目的**：让外部 server 起的任何名字都能塞进 OpenAI tool name 字符表（虽然 OpenAI 实际允许更多字符，但统一收口到安全子集，64 字符限制才好统计）。

### 64 字符限制（[L3220-3221](s14_mcp_plugin.py#L3220-L3221)）

```python
if len(prefixed) > 64:
    raise ValueError(f"MCP tool name is longer than 64 characters: {prefixed}")
```

**为什么是 64**：OpenAI / Anthropic 工具名普遍限制 64 字符。`mcp__` (5) + `__` (2) = 7 字符前缀，留 57 给 `server__tool`。**够用但有上限**——故意让 server 名短，让开发者感知"名字太长的 server 设计有问题"。

### 撞名检测（[L3223-3225](s14_mcp_plugin.py#L3223-L3225)）

```python
if prefixed in origins:
    raise ValueError("MCP tool name collision after normalization: "
                     f"{prefixed!r} maps both {origins[prefixed]} and {origin}")
```

`origins` 同时跟踪 built-in 工具和已加入的 MCP 工具，**双向上报**——"A 工具撞 B 工具时具体是哪两个"。`assemble_tool_pool()` 失败时**raise 而不是 silently overwrite**——这关系到授权边界，宁可连接失败也不要路由到错的 handler。

## 4. assemble_tool_pool 三大约束（每轮重建）

[（L3205-3246）](s14_mcp_plugin.py#L3205-L3246)

```python
def assemble_tool_pool() -> tuple[list[dict], dict[str, callable]]:
    global mcp_tool_policies
    tools = list(BUILTIN_TOOLS)
    handlers = dict(BUILTIN_HANDLERS)
    policies: dict[str, str] = {}
    origins = {tool["function"]["name"]: f"built-in tool {tool['function']['name']!r}"
               for tool in tools}
    for server_name, server in mcp_clients.items():
        # ... normalize, prefix, 撞名检测, schema 校验 ...
        handlers[prefixed] = (
            lambda *, client=server, tool=raw_name, **kwargs:
            client.call_tool(tool, kwargs)
        )
        policies[prefixed] = MCP_HOST_POLICY.get((server_name, raw_name), "confirm")
    mcp_tool_policies = policies
    return tools, handlers
```

### 关键设计：handler 闭包（[L3239-3242](s14_mcp_plugin.py#L3239-L3242)）

```python
handlers[prefixed] = (
    lambda *, client=server, tool=raw_name, **kwargs:
    client.call_tool(tool, kwargs)
)
```

**这里有个新手必踩的坑**：如果直接写 `lambda **kwargs: client.call_tool(raw_name, kwargs)`，**所有 lambda 会共享循环变量 `server` 和 `raw_name` 的最终值**——所有 handler 都指向"循环最后一项"。修复办法：
- `*, client=server, tool=raw_name` 用**关键字参数默认值**捕获当前值
- 每次循环迭代都生成一个独立闭包

**测试覆盖**（`_s14_functional.py`）：连 docs + deploy 两个 server 后，调用 `mcp__docs__search` 路由到 docs server，调用 `mcp__deploy__trigger` 路由到 deploy server，**不串台**。

### mcp_tool_policies 全局副作用（[L3207](s14_mcp_plugin.py#L3207) + [L3245](s14_mcp_plugin.py#L3245)）

`global mcp_tool_policies` + 最后赋值 = **状态通过全局变量同步**给 permission 模块（`check_permission` 读 `mcp_tool_policies`）。这是有意的：避免 permission 还要参数注入；其他模块读全局即可，assemble 完一定一致。

## 5. MCP_HOST_POLICY：host 决定，不信 server

### 三种状态（[L3116-3121](s14_mcp_plugin.py#L3116-L3121)）

```python
MCP_HOST_POLICY = {
    ("docs", "search"): "allow",
    ("docs", "get_version"): "allow",
    ("deploy", "status"): "allow",
    ("deploy", "trigger"): "confirm",
}
# 缺省值: "confirm"（[L3243](s14_mcp_plugin.py#L3243)）
```

| 状态 | 含义 |
|------|------|
| `allow` | 直接执行，不问用户 |
| `confirm` | 问用户（前台 turn 弹交互，teammate/后台线程直接拒绝） |
| 缺省 | `confirm`（**fail-closed**） |

### 为什么不信 `readOnlyHint`（注释 L3115）

```python
# 授权来自 host 配置，绝不信 server 的 readOnlyHint/destructiveHint；未配置默认 confirm
```

**原因**：server 是被 agent 控制的——agent 可以通过 prompt injection / 恶意 server 注入一个"声称只读但实际删数据"的工具。**信任根必须在 host**——只信 host 维护的精确 allowlist。这是"权限下沉"原则。

### check_permission 中的 mcp__ 路径（[L1150](s14_mcp_plugin.py#L1150)）

`check_permission` 检测到 `tool_name.startswith("mcp__")` 时查 `mcp_tool_policies[tool_name]`，按 allow/confirm 分发：
- `allow` → 立即返回 None（放行）
- `confirm` → 调 ask_user（前台） / 直接返回拒绝原因（teammate/后台）

## 6. connect_mcp 三种返回（[L3173-3183](s14_mcp_plugin.py#L3173-L3183)）

```python
def connect_mcp(name: str) -> str:
    if name in mcp_clients:
        return f"MCP server '{name}' already connected"
    factory = MOCK_SERVERS.get(name)
    if not factory:
        return f"Unknown server '{name}'. Available: {', '.join(MOCK_SERVERS)}"
    server = factory()
    mcp_clients[name] = server
    ...
```

| 情况 | 返回 | 模型行为 |
|------|------|----------|
| 重复连接 | "already connected" | 模型看到即可继续用 |
| 未知 server | "Unknown server ... Available: docs, deploy" | 模型据此修正 |
| 成功 | "Connected to ... Discovered N tools: ..." | 下一轮 assemble_tool_pool 就会出现新工具 |

**返回字符串 ≠ 异常**——所有情况都给模型字符串反馈，让它知道结果。`mcp_clients` 在调用后立刻更新，下一轮 `assemble_tool_pool` 就能看到。

## 7. agent_loop 的 1 行改动

[（L3499+）](s14_mcp_plugin.py#L3499) 里关键位置（需看实际代码）：

```python
# 旧版
tools, handlers = BUILTIN_TOOLS, BUILTIN_HANDLERS

# s14 后
tools, handlers = assemble_tool_pool()  # 每轮重建
```

**仅此一行**——所有 MCP 工具自动跟随。**这就是"插件不修改 loop"的精髓**。

## 10. 与后续章节的连接

- **s15 集成**：s14 已经把"MCP 工具动态进入工具池"打通，s15 只需要 `assemble_tool_pool()` 每轮跑 + system prompt 里追加"MCP 状态"段
- **权限下沉的延伸**：host 拥有最终授权 → s15 的 `MCP_HOST_POLICY` 是 host policy 的一例，权限闸在其他地方（bash deny list、file path 限制）也是同样模式
- **错误边界**：双 catch（内层 MCPClient + 外层 execute_named）模式可以推广到所有"外部能力调用"——任何来源不稳定的代码路径都该"异常转字符串"
