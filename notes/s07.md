# s07 - Skill Loading

## 1. 一句话核心

SYSTEM prompt 只放**技能目录**（name + description），完整的 `SKILL.md` 等模型调用 `load_skill` 时才按需加载进 messages——把"所有知识堆进 system prompt"换成"按需加载"。

教材原话：*"The system prompt contains the skill catalog; `load_skill` returns the full `SKILL.md`."*；Harness Layer 定位为 **Knowledge loading — show the model which skills exist, then load one by name**（README 第 7-9 行）。动机：React 规范、SQL 风格、API 设计全塞 SYSTEM 的话，每次 LLM 调用都发全部文档——改 React 时 SQL 和 API 文档照样占 input token（README 第 15-26 行）。

本项目实现见 [s07_skill_loading.py:43-94](s07_skill_loading.py#L43-L94)（SkillLoader）、[s07_skill_loading.py:100-110](s07_skill_loading.py#L100-L110)（SYSTEM 构建）、[s07_skill_loading.py:468-480](s07_skill_loading.py#L468-L480)（load_skill 工具）。

## 2. 渐进式披露（progressive disclosure）的核心思想

**只把"模型决定是否需要"的那一层信息放进 SYSTEM，完整内容延迟到被需要时。**

教材的内容分配表（README 第 36-39 行）：

| 内容 | 进模型的时机 | 占用的地方 |
|---|---|---|
| Skill name + description（目录） | 启动时 | system prompt（轻量，一直占） |
| Full `SKILL.md` | `load_skill` 被调用时 | `tool_result`（按需，才占） |

对照不渐进的做法（README 第 15-24 行）：`SYSTEM = base + open("react.md").read() + open("sql.md").read() + open("api.md").read()`——所有文档**固定**在 system prompt，每次调用都发。渐进式披露省的是"当前任务用不到的那些文档"的 token 和上下文空间。

## 3. 3 个核心机制

### ① 扫描 scan（[s07_skill_loading.py:67-81](s07_skill_loading.py#L67-L81)）
`glob("*/SKILL.md")` 扫 `skills/` 下每个目录，读文件 → `parse_frontmatter` 拆出 metadata 和正文 → 提取 `name`/`description` → 存进 `self.skills` 注册表（含完整 content）。

### ② SYSTEM 构建 build_system_prompt（[s07_skill_loading.py:100-110](s07_skill_loading.py#L100-L110)）
启动时调用**一次**（`SYSTEM = build_system_prompt()`），把基础指令 + `"Skills available:\n" + catalog` + "Use load_skill..." 拼好。静态，不每次 LLM 调用重扫。

### ③ 按需加载 load（[s07_skill_loading.py:88-94](s07_skill_loading.py#L88-L94)）
`load_skill` 工具按 name 查注册表，命中返回 `SKILL.md` 全文（作为 `tool_result` 进 messages）；未命中返回 `Error: Unknown skill 'X'. Available: ...`。

## 4. 4 层内容模型

| 层 | 内容 | 来源 | 进模型的时机 |
|---|---|---|---|
| 1. name | 技能名 | frontmatter `name`，否则**目录名**兜底（[L74](s07_skill_loading.py#L74)） | 启动时（catalog） |
| 2. description | 一句话描述 | frontmatter `description`，否则**正文第一行**兜底（[L75](s07_skill_loading.py#L75)） | 启动时（catalog） |
| 3. content | `SKILL.md` 全文 | 注册表里的 `content`（[L88-92](s07_skill_loading.py#L88-L92)） | `load_skill` 调用时（tool_result） |
| 4. error | `Unknown skill + Available` | `load` 未命中分支（[L93-94](s07_skill_loading.py#L93-L94)） | 错误时（tool_result） |

**关键**：name/description 进 SYSTEM 让模型"知道有哪些"，content 延迟到模型决定需要；error 层带 available 列表让模型能自我修正（重新选对名字）。

## 5. OpenAI 协议 vs Anthropic 协议差异

教材 s07 `code.py`（Anthropic）对项目 `s07_skill_loading.py`（OpenAI/DeepSeek），重点在 load_skill 工具注册：

| 维度 | 本项目（OpenAI） | 教材（Anthropic） |
|---|---|---|
| load_skill schema | `{"type":"function","function":{"name","description","parameters"}}`（[L468-477](s07_skill_loading.py#L468-L477)） | `{"name","description","input_schema"}` |
| SYSTEM 传递 | `messages[0]` 的 system 消息（main 里 history[0]） | `create(system=SYSTEM, ...)` 独立参数 |
| catalog 进 SYSTEM | `build_system_prompt()` 拼字符串（[L100-107](s07_skill_loading.py#L100-L107)） | 同样拼字符串，无差异 |
| 内容返回 | `load` 返回 str，直接作 tool content | 相同 |

**协议差异在 load_skill 上不大**——工具定义只是 schema 形状不同；本项目的 `load` 返回 str 在 OpenAI 协议下直接作 tool 消息 content（[L479-480](s07_skill_loading.py#L479-L480)），Anthropic 下同样返回 str。

## 6. 本项目对参考代码的 N 项适配

1. **build_system_prompt 的 base 保留 todo_write 规划引导**（[L102-103](s07_skill_loading.py#L102-L103)）：教材 base 只有 "Act, don't explain"；项目合并了 s05 的规划指令
2. **空目录处理**：`catalog()` 空时返回 `"none"`（[L84-85](s07_skill_loading.py#L84-L85)）；`build_system_prompt` 检测空目录 → 显示 `"No skills loaded."` 而非 `"Skills available: none"`（[L104-105](s07_skill_loading.py#L104-L105)）——避免 SYSTEM 里出现误导性的 "none" 让模型以为有叫 none 的 skill
3. **read_text 带 `errors="replace"`**（[L72](s07_skill_loading.py#L72)）：SKILL.md 编码不兼容时不崩
4. **保留 s06 全部能力**：subagent/task、todo_write、权限闸门、5 hook、surrogate/stdin 适配全在原样（docstring 第 4-5 行）；TOOLS 现在是 8 个（6 基础 + task + load_skill）
5. **bound method 身份比较的发现**（测试层）：`TOOL_HANDLERS["load_skill"] is SKILL_LOADER.load` 断言不成立——Python 绑定方法每次访问创建新对象，`is` 身份比较对 bound method 不可靠，改用功能验证（调用它返回 skill 内容）

## 7. N 个最佳实践亮点

1. **`yaml.safe_load` 而非 eval**（[L60](s07_skill_loading.py#L60)）：frontmatter 解析不执行任意代码
2. **name/description 兜底链**（[L74-75](s07_skill_loading.py#L74-L75)）：frontmatter 优先，目录名/正文首行兜底——SKILL.md 缺字段也能进 catalog
3. **`load` 查字典不解释为路径**（[L88-89](s07_skill_loading.py#L88-L89)）：skill 名不是文件路径，天然防路径越权
4. **错误带 available 列表**（[L93-94](s07_skill_loading.py#L93-L94)）：模型打错名能读到可用列表自我修正
5. **SYSTEM 静态构建**（[L110](s07_skill_loading.py#L110)）：启动时 scan 一次，不每次 LLM 调用重扫目录
6. **空目录不误导**（[L104-105](s07_skill_loading.py#L104-L105)）："No skills loaded." 而不是 "Skills available: none"
7. **catalog 只暴露 name+description**（[L83-86](s07_skill_loading.py#L83-L86)）：轻量目录，完整 content 不进 SYSTEM——渐进式披露的直接实现
8. **load_skill 走 TOOL_HANDLERS 同一条 dispatch**（[L480](s07_skill_loading.py#L480)）：和 task/其它工具一样，不需要改 loop

## 8. ⚠️ 主观理解待补充 [❓ 用户补充]

代码能客观看出的摩擦点（作为线索）：

- `build_system_prompt` 里 skills 段落是**启动时**拼的（静态），如果运行时往 `skills/` 加了新 skill，需要重启才生效——没有热重载机制
- `load` 返回 `SKILL.md` 全文，若 skill 文件很大，tool_result 会占上下文——skill 内容本身没有被截断（不同于 run_bash 的 50000）
